# WTT result freshness

Compare the official event's `take_10_official_results.json` response with the same URL carrying a current `q` timestamp. A 200 response can still contain yesterday's results; compare `matchDateTime.startDateUTC`, scores and response modification time. The unversioned Azure CDN URL has been observed returning older results than the timestamped URL.

Use the refresh timestamp on official-result requests, as on the event-list request. Keep JSON, `/api/events` and topic ICS on `getTopicCalendarCacheKey('wtt')`; invalidate pre-fix data through a shared cache version. WTT has a five-minute server cache, distinct from other topics. SWR can return the old payload once while revalidating, and the browser's range payload cache can require a reload.

Count schedule and result requests together. The event list includes future tournaments: only fetch official results when the tournament's normalized start time is at or before now, while retaining the 30-day end-time horizon. On 2026-10-09, fetching future tournaments' empty result files generated 64 external requests; production logs confirmed `Too many subrequests by single Worker invocation`, and today's results were silently dropped by `Promise.allSettled`. Local Worker success alone did not reproduce the production limit. Log rejected result requests and cancel unread response bodies on 204/404/error paths to release Worker connections. When changing cache versions, retain completed results from the previous version and keep the five-minute TTL aligned with the new key.

The official file contains only ten matches. Merge recently observed completed results into the next payload so a refresh does not remove prior matches. Retain the existing 30-day horizon, discard cached schedules, deduplicate by existing ID and let fresh results replace older scores. This preserves observed results; it does not recover matches that were never fetched. Do not infer a score from elapsed time.

The loader caches the event list for one hour, each future schedule for six hours, and active schedules/results for five minutes. Ended-event results get a first refresh after the normalized end timestamp, then daily correction checks; cache records remain stored for 60 days. These checks run on demand during aggregate refreshes, not an independent polling job. Keep the per-refresh upstream request budget at 40, reserve requests before fetching, and load results before schedules. With KV available, deferred uncached schedules progress on later refreshes because cached resources do not consume the budget. Upstream failures use the previous per-event payload without advancing its successful-check timestamp. Regression tests cover active/ended transitions, daily retries, cached fallback and more than 80 future tournaments. The budget controls WTT fetch calls only; redirects and other calendar loaders still share the invocation's platform limit.

Validate regression cases for timestamp-dependent upstream responses, retained prior-day results, corrected scores, expired history and unchanged ICS UIDs. Follow AGENTS.md checks, then request JSON, event API and WTT ICS from dev and verify at least one current-day official result. Report local verification separately from deployment.

Do not discard a schedule unit merely because its planned start or end has passed. Retain unresolved matches for the current 24-hour window, and retain explicitly live matches until their status changes. Only explicit upstream live statuses set `isLive`; elapsed time or `ActualStartDate` alone is insufficient (the official feed also prepopulates actual-time fields on scheduled entries). The schedule response can contain duplicate codes with conflicting statuses: prioritize terminal statuses, then live, then Start List, then Scheduled so obsolete copies do not resurrect completed matches. Regression-test past-start/past-end retention, explicit live status, terminal removal, duplicate priority and unchanged IDs. The visible client calendar refreshes every five minutes so an open view receives status/result updates.

On Windows, Node fetch may ignore proxy environment variables. Curl can retrieve the response through the configured proxy, but some bundled curl versions cannot decode Brotli: inspect `Content-Encoding`, and use Node's `brotliDecompressSync` on the downloaded response for analysis. Do not confuse a local decoding failure with the Worker's upstream failure.
